# スキル

*[English](./skills.md)*

このパッケージに収録された全スキル(6 件)のカタログです。各スキルに 1〜2 行の概要を添えています。

各スキルは `kit/skills/<name>/` に置かれ、間にドメインのディレクトリはありません。そのフォルダ名が、そのスキルの `name:` であり、インストール後のフォルダ名でもあります。したがって以下の **スキル** 欄だけで足ります — `/name` として呼び出す名前、配置後に `.claude/skills/` に現れる名前、ソースの在処が、すべて同じ 1 つの文字列です。接頭辞はハイフンを含む 4 文字で、その 3 文字目がライブラリを表します。配置と命名の規則は [ビルド規約](https://github.com/openreachtech/hora-skills-ort-support/blob/main/.claude/skills/build/SKILL.md) を参照してください。各スキルの詳しい手順は、それぞれの `SKILL.md` と、その隣の `references/` にあります。ここでは 6 件すべてが `references/` を持ち、どの参照が何を定めるかは各 `SKILL.md` が示します。

| スキル | 概要 |
| :-- | :-- |
| `hos-explain` | AI が出した説明・報告・提案を、図を交えた平易な言葉に書き直す。技術的な背景を持たない読み手が一読で理解できることを基準とする。既存の内容を書き直すだけで、新しい分析は加えない。 |
| `hos-humanize-docs` | 保守されている文書を、初めて読む人が詰まらない状態に直す。前提知識のないエージェントが詰まった箇所を報告し、それを明文化された基準に照らして分類して直し、報告数が閾値に収まるまで繰り返す。構造・文体・想定読者は変えない。 |
| `hos-skillify` | いま進行している会話からスキルを作る。トランスクリプトを掘り、何が持続する規約かを判断し、結果をスキル作成の規約へ引き渡す。規約でないと判明した材料は、報告した上で捨てる。 |
| `hos-user-manual` | 実際にシステムを動かして利用者向けの操作マニュアルを生成する。稼働環境の UI を機能ごとに辿り、スクリーンショット付きの HTML ページを機能ごとに 1 枚、加えて目次ページを、製品バージョンに紐づくディレクトリの下に書き出す。 |
| `hos-write-issue` | この組織の GitHub issue を書く。種別の emoji を持つタイトルと、`As-is` / `To-be` / `Note` / `Checklist` / `Sub-issues` の本文を、そのまま入力欄へ貼れるようフェンスで囲んで渡す。issue が述べるのは現状と方針で、どう作業したかは pull request のもの。 |
| `hos-write-pull-request` | pull request を書く。紐づく issue の種別 emoji を持つタイトルと、閉じる issue を載せる `# Why`、採った方針を述べる `# How`、注意が要るときだけ置く `# Note` の本文を、フェンスで囲んで渡す。述べるのはどう作業したかで、trunk をマージする PR が有効にする merge only の行も扱う。 |

## 境界

6 つは概要から受ける印象ほど重なりません。それぞれの `SKILL.md` が「自分ではやらず、どこへ渡すか」を明記しています。

- **`hos-explain` は書き直すだけで、調査はしません。** 渡されるのは既に出ている答えで、それを、流れを追っていない人にも読める形にします。新しい分析が要る問いは、その分析を担う規約のものです。
- **`hos-humanize-docs` は文書を直すもので、別の読者向けに書き直すものではありません。** 構造・文体・想定読者はそのままで、専門語も残します。分野の外の人が読めるように作り直すのは `hos-explain` の仕事です。
- **`hos-user-manual` は製品の利用者向けで、開発者向けではありません。** 辿るための稼働環境が必要で、その環境を構築するのは backend パッケージの仕事です。成果物は顧客が読むマニュアルです。
- **`hos-write-issue` が作るのはテキストだけで、起票はしません。** issue を立てること、`# Sub-issues` の行をサブイシューに変換すること、チェックを入れることは人の操作です。述べるのは現状と方針で、どう作業したかは pull request に委ねます。
- **`hos-write-pull-request` が述べるのは、どう作業したかだけです。** なぜやるのかは issue へのリンクで済ませ、現状と方針を書き直しません。それらは issue のもので、二重に書けば、どちらかを直した瞬間に食い違います。
- **`hos-skillify` が作るのはスキルだけです。** 決着した会話から持続する部分を取り出し、名前・`description:`・ファイル配置は、引き渡し先のスキル作成規約に委ねます。

## 導入

```sh
npm install -D @openreachtech/hora-skills-ort-support
npx --no hora-skills-ort-support install
```

`postinstall` フックの宣言、複数ドメインを同じ `.claude/skills/` に入れる方法、配置を最新に保つ方法は [README](https://github.com/openreachtech/hora-skills-ort-support/blob/main/README.ja.md) にあります。
